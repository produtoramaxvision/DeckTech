# LANDING surface — analysis (dokke.vercel.app)

Scope: `docs/` — the Vite-built marketing site deployed at dokke.vercel.app. Covers
`docs/index.html`, `docs/src/main.js`, `docs/src/style.css`, `docs/package.json`,
`docs/vite.config.js`, `docs/public/tutorial-dokke.html`, `docs/public/*` and
`docs/assets/*`. All line numbers are `path:line` into the files as read on 2026-09-17.

## 1. Build system

`docs/package.json:1-13` — a standalone npm/Vite project, **separate from the repo root**
(no shared `package.json`, no workspace reference visible from this surface). Three scripts:
`dev`, `build` → `vite build`, `preview`. Single devDependency: `"vite": "^8.2.1"`
(`docs/package.json:11`).

`docs/vite.config.js:1-9` — minimal `defineConfig`: `base: "/"`, `build.outDir: "dist"`,
`build.emptyOutDir: true`. No plugins, no alias, no asset-inlining threshold override, no
`define`. `import.meta.env.BASE_URL` (used at `main.js:8`) resolves to `base` (`"/"`), which
is why `dokke-hero.webp` is fetched from `/dokke-hero.webp` at the site root and not
`/docs/dokke-hero.webp` — Vercel's build must publish `docs/dist` as document root.

`docs/index.html:1-16` is the only HTML entry Vite processes; it mounts `<div id="app">` and
loads `/src/main.js` as an ES module (`docs/index.html:14`). Everything else — every
section, every string, all navigation — is generated by `main.js` writing to
`#app.innerHTML` at runtime (`main.js:51-253`). **There is no server-rendered or
static-in-HTML content beyond the `<head>` meta tags.** A crawler or a social-card
unfurler that does not execute JS receives an empty `<div id="app"></div>` and the
generic `<title>`/`<meta description>` from `index.html:7-9`. There is no `og:*`, no
`twitter:card`, no canonical link, and no JSON-LD anywhere in `index.html` or `main.js`.
For a public marketing/install page this is the single biggest structural weakness on
this surface — worse than any CSS or copy issue below.

`docs/public/` is served as-is at the site root by Vite's public-dir convention
(`dokke-favicon.png`, `dokke-hero.webp`, `dokke-icon.png`, `tutorial-dokke.html`).
`docs/assets/dokke-iphone.png` (1.5MB, `docs/assets/`) is **not** under `docs/public/` and
is not referenced anywhere in `docs/index.html`, `docs/src/main.js`, `docs/src/style.css`,
or `docs/public/tutorial-dokke.html` (verified: `grep -rn "dokke-iphone" docs/` returns
nothing). It is only referenced from the repo root `README.md:30`
(`<img src="docs/assets/dokke-iphone.png" ...>`), i.e. it belongs to the GitHub README, not
to the deployed landing site. It is out of scope for this surface's build but is a
Dokke-branded asset a full rebrand still must touch.

## 2. Page structure (docs/src/main.js:51-253)

Single template-literal string assigned to `#app.innerHTML`. Sections, in DOM order:

1. **`.hero-page` / `#section-01`** (`main.js:52-102`) — full-viewport hero wrapper containing:
   - `.code-pattern` decorative background (`main.js:53`, styled `style.css:44-62`) — 15
     repeated rows of a hardcoded ASCII/binary string (`main.js:10-14`), each offset by
     `index % 3` character-widths for a parallax-looking static texture.
   - `<header class="site-header">` → `.nav-shell`: wordmark ("Dokke") + nav links
     (Recursos/Comunidade/Docs/GitHub) + `.nav-actions` (language toggle PT/EN +
     GitHub pill button with inline SVG logo) (`main.js:55-75`).
   - `<main><section class="hero">` (`main.js:78-99`): `.hero-emblem` button wrapping
     `.hero-icon` (the interactive parallax image), eyebrow line, `<h1>`, hero copy,
     `.hero-actions` (two `.primary-button` CTAs — macOS DMG, Android APK — separated by a
     `.cta-plus` "+"), `.hero-meta` line, `.windows-note` ("Em breve · Dokke para
     Windows").
2. **`.features-section#features`** (`main.js:104-136`) — 3-card asymmetric grid: a
   2-column-span dark card, a 1-column light card, and a full-width "wide" card with 4
   inline feature-point pills.
3. **`.roadmap-section#roadmap`** (`main.js:138-170`) — two-column layout: sticky-feeling
   heading + intro + a hardcoded `.version-badge` ("disponível agora · v0.2.8"), and a
   5-row list of roadmap items, the first marked `--available` (green status), the rest
   "spoiler".
4. **`.community-section#community`** (`main.js:172-206`) — heading/intro/CTA column +
   3 `.community-action` link rows (BUG / IDEIA / AJUDA) + an embedded `.community-club`
   dark card cross-promoting the unrelated "Documente Club" product
   (`communityUrl = "https://documenteclub.vercel.app/"`, `main.js:7`, `main.js:198-203`).
5. **`.faq-section#faq`** (`main.js:208-242`) — native `<details>/<summary>` accordion, 6
   Q&As, no JS needed for open/close (uses the browser's built-in disclosure widget).
6. **`<footer class="site-footer">`** (`main.js:244-252`) — wordmark link back to top,
   copyright note, 3 social links (Instagram, X, GitHub).

After the template is injected, `main.js:255-328` defines `LANDING_SELECTORS` (a
selector → i18n-key map) and `applyLandingLanguage()`, which walks every entry and
overwrites `textContent`/`aria-label`/`innerHTML` per key, then separately patches
`.windows-note`, the 4th feature card's point-pills, and the language-toggle buttons'
`aria-pressed`. This runs once at load (`main.js:328`) and again on every language-toggle
click (`main.js:321-327`).

### `docs/public/tutorial-dokke.html` (self-contained, not part of the Vite bundle)

A **separate, fully self-contained HTML document** (own `<style>` block, own inline
`<script>`, no import of `main.js` or `style.css`) reached at `/tutorial-dokke.html`.
It is a 15-slide, keyboard/click-navigable narrative deck telling Dokke's origin story
("De celular velho a produto real"): cover → origin → pivot → the Instagram video →
what-the-product-is → architecture (Mac host / Android client / "one tap" result) →
under-the-hood → AI-in-the-process → first MVP → open-source → community →
release-readiness → what-exists-today → roadmap → closing CTA (slide ids at
`docs/public/tutorial-dokke.html:744-975`). Navigation: `←`/`→` buttons, arrow keys,
Page Up/Down, Space, Home/End, and `location.hash` sync so a slide is deep-linkable
(`docs/public/tutorial-dokke.html:986-1024`). It defines its **own** design-token palette
(`--orange`, `--orange-deep`, `--cream`, `--paper`, `--ink`, `--muted`, `--line`,
`--green`, `docs/public/tutorial-dokke.html:10-19`) — visually consonant with, but
**not sharing a single token** with, `docs/src/style.css:1-13`'s `--ink`, `--muted`,
`--soft`, `--hero-orange`, `--hero-orange-light`, `--blue`, `--purple`. That is a real,
citable duplication: two independent design-token sets encoding the same brand colors
under different names, with zero mechanism keeping them in sync.

## 3. Animation & scroll system (docs/src/main.js)

- **Language switching** (`main.js:36-49, 299-328`): `detectLandingLanguage()` reads
  `navigator.language`, defaults to `"pt-BR"` unless it starts with `"pt"` is false, in
  which case `"en"`. Persisted to `localStorage` under key `LANDING_LANGUAGE_KEY =
  "dokke_landing_lang"` (`main.js:16`, read/write wrapped in `try/catch`).
- **Hero pointer-parallax motion** (`main.js:330-413`), gated three ways before it ever
  runs: `heroEmblem && heroSection` exist, **and** `finePointer.matches` is true at
  **module-evaluation time** (`main.js:332, 335` — `window.matchMedia("(hover: hover) and
  (pointer: fine)")` is read once with no `change` listener attached anywhere in the file;
  a user who docks a mouse after page load never gets the effect activated, since the whole
  `pointermove`/`pointerdown` listener block lives inside that `if`).
  - `pointermove` on `.hero`(`main.js:397-409`) computes normalized cursor position
    relative to the hero's bounding rect, converts to `motionX`/`motionY` clamped to
    `[-4, 4]` px (`* 8` then `clamp`, `main.js:404-405`) and `rotation` clamped to
    `[-2, 2]` deg (`main.js:406`), skipped entirely when `pointerType !== "mouse"` or
    reduced-motion is active (`main.js:398`).
  - Writes are coalesced through `requestAnimationFrame`: `scheduleMotion()` only queues
    a frame if one isn't already pending (`main.js:358-360`), and `renderMotion()` resets
    `frame = 0` and writes three CSS custom properties (`--hero-mx`, `--hero-my`,
    `--hero-rotate`) that the CSS transform reads (`main.js:343-356`, consumed at
    `style.css:169`). This is a textbook single-write-per-frame pattern — no layout
    thrashing, no redundant style writes.
  - `pointerdown`/`pointerup`/`pointercancel`/`pointerleave` on the emblem toggle
    `.is-hero-pressed` (`main.js:377-384`), and `Enter`/`Space` keydown/keyup do the same
    for keyboard users (`main.js:386-395`), preventing default so Space doesn't scroll the
    page.
  - `pointerleave` on the whole `.hero` section calls `resetHeroMotion()`, zeroing
    `motionX/motionY/rotation` and stripping `is-hero-tracking`/`is-hero-pressed`
    (`main.js:362-368, 411`).
  - A `reducedMotion.addEventListener("change", resetHeroMotion)` (`main.js:412`) is the
    **only** listener that reacts to a live OS-level reduced-motion toggle, and it too is
    scoped inside the `finePointer.matches` gate, so it never attaches at all on a
    coarse-pointer/no-hover device (mobile) — moot there since there's no pointermove
    parallax to begin with, but worth knowing before assuming "reduced motion is always
    respected live."
- **No scroll-triggered animation exists on this surface.** There is no
  `IntersectionObserver`, no scroll listener, no reveal-on-scroll class toggling anywhere
  in `main.js`. `html { scroll-behavior: smooth }` (`style.css:16`) is the only scroll
  behavior, for the in-page anchor links (`#features`, `#community`, `#section-01`).
  "Scroll system" on this surface is exactly one CSS declaration plus native anchor
  scrolling — there is no JS-driven parallax-on-scroll, sticky-reveal, or stagger system
  to document beyond that.
- **`.hero-emblem` is a `<button>` with `aria-label="Pressionar o ícone do Dokke"`
  (`main.js:79`) that performs no action on activation** — no click handler exists, only
  the press-state visual toggle. It announces to assistive tech as an interactive control
  that does nothing when activated; a screen-reader or switch-control user who "presses" it
  gets zero feedback beyond a CSS transform, and it doesn't navigate or open anything.

## 4. Test contract — `test/docs-hero-motion.test.mjs` (repo root, not under `docs/`)

This test is the load-bearing spec for the hero motion + branding assets and is a hard
constraint on any DeckTech rebrand of this surface. It asserts, file by file:

- `docs/public/dokke-hero.webp` exists, byte length `(0, 100*1024)`.
- `docs/public/dokke-favicon.png` exists, byte length `(0, 20*1024)`.
- `docs/index.html` contains the **exact literal string**
  `<link rel="icon" type="image/png" sizes="64x64" href="%BASE_URL%dokke-favicon.png" />`.
- `docs/public/tutorial-dokke.html` contains the **exact literal string**
  `<link rel="icon" type="image/png" href="/dokke-favicon.png" />` — note this is an
  **absolute, non-`BASE_URL`-templated** path, inconsistent with `index.html`'s
  `%BASE_URL%`-templated form; the test enshrines that inconsistency rather than catching it.
- `docs/src/main.js` contains, as regex-matched substrings: the literal
  `const dokkeHeroIcon = \`${import.meta.env.BASE_URL}dokke-hero.webp\`;` declaration, its
  `src="${dokkeHeroIcon}"` usage, `<button type="button" class="hero-emblem"`, the
  `matchMedia("(hover: hover) and (pointer: fine)")` and
  `document.querySelector(".hero")` lines, the `pointermove`/`pointerdown`/`pointerup`
  listener registrations, the `is-hero-pressed` class name, `requestAnimationFrame`, the
  `pointerleave` listener, and `prefers-reduced-motion`.
- `docs/src/style.css` contains, as regex-matched substrings: `transform: translate3d(var(--hero-mx…`,
  a `transition: transform` rule, the `.hero-emblem.is-hero-pressed .hero-icon` selector,
  `scale(.95)`, the exact hero-icon dimensions (`width: 204px; height: 204px;` desktop,
  `width: 124px; height: 124px;` inside `@media (max-width: 760px)`), the `.hero` padding
  formula (`padding: clamp(60px, 9.5vh, 108px) 20px 70px;`) and its mobile override
  (`padding-top: 56px;`), the `h1` responsive `font-size` clamps at both the 760px and
  420px breakpoints, and the full `@media (prefers-reduced-motion: reduce)` block forcing
  `transform: none !important; transition: none !important;` on `.hero-icon`.

**Consequence for a rebrand:** renaming `dokke-hero.webp`/`dokke-favicon.png` on disk, the
`dokkeHeroIcon` identifier, or any of the byte thresholds / pixel dimensions / breakpoints
above will fail this test until the test itself is updated in lockstep. The safest
DeckTech path is either (a) keep the asset filenames and JS identifier unchanged and only
swap pixel content, or (b) rename everything (files + `main.js` + both HTML `<link>`
lines + this test) in one atomic commit — never partially.

## 5. CSS design system (docs/src/style.css, 864 lines)

### Tokens (`style.css:1-13`, `:root`)
```
--ink:               #1d1d1f
--muted:              #77747d
--soft:               #a9a6ad
--hero-orange:        #ff8a38
--hero-orange-light:  #fff1e6
--blue:               #1633f9   (focus rings, selection background — link color is never var(--blue) in body copy)
--purple:             #9653f4  ← declared, never referenced again anywhere in style.css or main.js (dead token)
--max-width:          1120px
```
`color-scheme: light` is hardcoded (`style.css:10`) — there is no dark-mode variant of
this surface at all; every color below is a literal light-theme value, many inlined as
one-off hex/rgba rather than routed through a token (e.g. `#77747d` for muted text is
repeated directly at `style.css:396, 460, 519, 553, 619, 663, 741` instead of referencing
`var(--muted)`, which is declared at `style.css:3` for exactly this purpose — token
declared, then bypassed by direct hex on 7+ call sites).

`font-family: Inter, ui-sans-serif, -apple-system, BlinkMacSystemFont, "Segoe UI",
sans-serif;` (`style.css:11`) with `font-synthesis: none` (`style.css:12`). **No
`@font-face`, no Google Fonts `<link>`, no `fonts.googleapis.com`/`fonts.gstatic.com`
reference, and no `.woff`/`.woff2` file anywhere in `docs/`** (verified via grep across
`docs/`). Inter is never actually loaded by this page. Combined with `font-synthesis:
none` — which explicitly forbids the browser from faking a missing weight — every
`font-weight: 750`/`650`/`700` declaration (used throughout for `h1`, section headings,
feature-card titles) silently falls back to whatever weight the visitor's OS ships for
`-apple-system`/`Segoe UI`/system sans, typically 400 or 700 only. On Windows specifically
(`"Segoe UI"` is in the stack) this means the type system's whole weight ramp — the thing
that gives this design its punch — is not rendering as designed for any visitor today,
Windows or otherwise. This is the largest single design-fidelity gap on the surface and
directly relevant to a "first-class Windows host" brand, since Windows visitors are
exactly the audience currently getting the degraded fallback.

### Palette / glass / blur treatments
- `.hero-page` background (`style.css:26-29`): a radial highlight
  (`radial-gradient(ellipse 48% 36% at 50% 27%, rgba(255,255,255,.52), transparent 78%)`)
  layered over a vertical gradient from a 22%-mixed orange tint through
  `--hero-orange-light` to white — `linear-gradient(180deg, color-mix(in srgb,
  var(--hero-orange) 22%, white) 0%, var(--hero-orange-light) 48%, #fff 82%)`. Uses modern
  `color-mix()` (no fallback declared — acceptable for evergreen Chromium/Firefox/Safari
  but worth flagging as a compat assumption).
  - `.hero-page::after` (`style.css:31-42`): an oversized blurred white ellipse
    (`filter: blur(34px)`) forming a soft "floor" glow beneath the fold.
- `.nav-shell` (`style.css:71-83`): the header pill is genuine glassmorphism —
  `background: rgba(255,255,255,.72)`, `border: 1px solid rgba(255,255,255,.76)`,
  `backdrop-filter: blur(17px)`, plus a dual box-shadow (`0 9px 24px rgba(74,62,111,.08)`
  outer + `0 1px 2px rgba(255,255,255,.9) inset` for a top highlight). This is the site's
  clearest, most deliberate glass treatment.
- `.code-pattern` (`style.css:44-62`): decorative background text, faded via
  `mask-image: linear-gradient(180deg, #000 0%, rgba(0,0,0,.85) 48%, transparent 100%)`
  and `opacity: .82`, `color: rgba(255,255,255,.64)` — a subtle top-of-hero texture, not a
  blur but functions as one visually against the orange gradient.
- Warm-tint surfaces reused for grouped sections: `feature-card--wide` background
  `#fff6ee` (`style.css:368`), `.community-section` background `#fff6ee`
  (`style.css:527`), `.faq-section` background `#fafafa` (`style.css:691`) — a consistent
  "warm card, neutral section" rhythm.
- Dark-surface cards (`.feature-card--dark` `style.css:355-360`, `.community-club`
  `style.css:632-638`) both use flat `#1d1d1f` (== `--ink`), not the token, again — same
  token-bypass pattern as `--muted`.

### Typography scale
- Display: `h1` and section `h2`s: `font-size: clamp(48px, 6.7vw, 82px)` (hero, `style.css:202`)
  / `clamp(44px, 5.5vw, 72px)` (section headings, `style.css:326`), `font-weight: 750`,
  `letter-spacing: -.075em`, `line-height: .98` — an aggressive, ultra-tight, ultra-bold
  display treatment (assuming Inter actually loads — see above).
- Feature-card `h3`: `clamp(25px, 2.5vw, 35px)`, weight 650, `letter-spacing: -.055em`
  (`style.css:379-387`).
- Body copy: hero copy 17px/1.7 (`style.css:210-216`), feature/roadmap/community body
  13-15px at 1.65-1.7 line-height — consistently generous leading for a display-heavy page.
- Kicker/eyebrow/label text: 9-11px, weight 700, `letter-spacing: .1em`-`.16em`,
  uppercase where relevant (`style.css:190-196, 312-319`) — the small-caps/tracking
  treatment used for every "section number" label (`01 /`, `02 /`, etc.).
- Monospace: `.code-pattern` only, `"SFMono-Regular", Consolas, monospace`
  (`style.css:55`) — the sole non-Inter font family reference on the page, and notably it
  **does** include a Windows-native fallback (`Consolas`) that the primary body font stack
  does not carry with the same intent (`"Segoe UI"` is present but Inter itself isn't
  reachable at all, per the font-loading gap above).

### Breakpoints
Exactly two, both `max-width` (mobile-first is not used — base styles are desktop,
overridden downward):
- `@media (max-width: 760px)` (`style.css:799-822`): collapses `.nav-links` entirely
  (`display: none`, `style.css:802`) with **no hamburger menu or alternate access to
  Recursos/Comunidade/Docs** — those three links become completely unreachable on mobile,
  reachable only via `#features`/`#community` if a user manually scrolls, and "Docs"
  (an external GitHub link) has no mobile entry point at all. Also re-flows the hero,
  shrinks the emblem to 132×132/icon to 124×124, stacks `.faq-shell`/`.roadmap-shell`/
  `.community-shell` to one column.
- `@media (max-width: 420px)` (`style.css:824-864`): further shrinks headings, stacks
  `.hero-actions` to `flex-direction: column` (`style.css:832`), tightens paddings
  throughout, restacks `.site-footer` to a flex column.
- `@media (prefers-reduced-motion: reduce)` (`style.css:789-797`) is treated as a
  breakpoint-equivalent global override: `*, *::before, *::after { scroll-behavior: auto
  !important; transition-duration: .01ms !important; }` plus an explicit `.hero-icon`
  transform/transition kill. The blanket `*` selector is broader than the stated intent —
  it also kills `.primary-button:hover`'s `transition: transform .2s ease, box-shadow .2s
  ease, background .2s ease` (`style.css:250`) and every other hover transition on the
  page (nav links, GitHub pill, community CTA, etc.), not just the hero parallax. A user
  with reduced-motion enabled loses all hover polish site-wide, which is a broader blast
  radius than "disable the parallax effect" implies.

### Motion curves (all instances)
- Hero icon idle: `transition: transform 520ms cubic-bezier(.22, 1, .36, 1), filter 520ms
  cubic-bezier(.22, 1, .36, 1);` (`style.css:171`).
- Hero icon while actively tracking pointer: duration drops to `140ms` via
  `.hero-emblem.is-hero-tracking .hero-icon { transition-duration: 140ms; will-change:
  transform; }` (`style.css:174-177`) — `will-change` is scoped to this class only, so the
  browser isn't asked to promote the layer permanently, only while the user is actively
  moving the pointer over the hero.
- Hero icon pressed: duration drops further to `90ms`
  (`.hero-emblem.is-hero-pressed .hero-icon`, `style.css:179-183`), paired with `scale(.95)`
  and a tighter/darker `drop-shadow(0 8px 9px rgba(222,105,33,.32))` replacing the idle
  `drop-shadow(0 20px 17px rgba(222,105,33,.22))` (`style.css:168`) — shadow collapses in
  sync with the scale-down, selling a physical "press into the surface" read.
- Everywhere else: a uniform `.2s ease` (occasionally `.35s ease` for the tutorial's
  progress bar) on `transform`/`background`/`box-shadow`/`color`/`border-color` —
  nav links, CTA buttons, community actions, footer links, language toggle. No custom
  easing curve is used anywhere outside the hero icon; the cubic-bezier treatment is
  reserved specifically for the one signature interaction.

## 6. Translation-system bugs (functional, not merely cosmetic)

The `LANDING_SELECTORS` / `applyLandingLanguage()` mechanism (`main.js:255-328`) has
several real gaps a rebrand should either fix or knowingly re-implement:

- **FAQ 5's `<b>` markup is destroyed on load.** The FAQ-5 answer is authored directly in
  the template with inline bold tags — `<b>Dokke.app</b>`, `<b>Abrir</b>`, `<b>Ajustes do
  Sistema → Privacidade e Segurança → Segurança → Abrir Mesmo Assim → Abrir</b>`
  (`main.js:234`). But `LANDING_SELECTORS` maps `.faq-list details:nth-child(5) p` to
  `["faq.5.a"]` with **no `"html"` mode flag** (`main.js:294`), so `applyLandingLanguage()`
  falls through to its default branch, `element.textContent = copy[key]`
  (`main.js:306`) — and the PT/EN copy values for `faq.5.a` (`main.js:24, 32`) are plain
  text with no markup. Since `applyLandingLanguage()` runs unconditionally on every load
  (`main.js:328`), the bold emphasis is wiped every time, in both languages — it only
  ever appears for the instant before the script runs.
- **The version badge never localizes.** `.version-badge` hardcodes `disponível agora ·
  v0.2.8` directly in the PT-only template (`main.js:144`) with no corresponding
  `LANDING_SELECTORS` entry. Both language dictionaries define a `roadmap.available` key
  (`"disponível agora"` / `"available now"`, `main.js:22, 30`) that is **never read by any
  code** — a translated string that exists but is wired to nothing. Switching to EN
  leaves "disponível agora · v0.2.8" on screen.
- **Same bug class, two more instances:** `.community-action-type` chip text ("BUG",
  "IDEIA", "AJUDA", `main.js:183, 188, 193`) is hardcoded in the template with no
  `LANDING_SELECTORS` entry and no copy keys at all — untranslatable by design, not by
  omission. Feature-card-1's `.feature-points` pills ("Mac host", "Android", "PWA",
  `main.js:116`) are likewise hardcoded and untranslated, while feature-card-3's
  equivalent pills **are** wired up via the `feature.3.points` pipe-delimited string and
  the manual `.forEach` at `main.js:311-314` — an inconsistent pattern across three
  visually identical pill rows.
- **`LANDING_LANGUAGE_KEY = "dokke_landing_lang"`** (`main.js:16`) bakes the brand name
  into the persisted localStorage key. A DeckTech rebrand that changes this string
  silently loses every returning visitor's saved language preference unless the old key
  is read once as a migration fallback.

## 7. Every Dokke-branded string, asset, and URL a DeckTech rebrand must change

### Text strings (PT and EN dictionaries both — `main.js:17-34`)
- Every `hero.*`, `features.*`, `roadmap.*`, `community.*`, `faq.*`, `footer.*` value that
  contains the word "Dokke", "Mac"/"macOS", or references "seu Mac" as the exclusive host —
  this is nearly every string in both dictionaries; the copy is written **Mac-first, not
  platform-neutral**. Concretely:
  - `hero.eyebrow`: "DOKKE · SEU MAC, EM QUALQUER TELA" / "DOKKE · YOUR MAC, ON ANY SCREEN"
    (`main.js:20, 28`).

## 8. Judgement

### Preserve verbatim — genuinely excellent, load-bearing design work
1. **The hero icon's three-tier motion ramp.** Idle `520ms cubic-bezier(.22, 1, .36, 1)`
   (`style.css:171`) → actively-tracking `140ms` (`style.css:174-177`) → pressed `90ms`
   (`style.css:179-183`). Three distinct speeds for three distinct interaction states is a
   level of motion-craft most marketing sites skip entirely (they use one duration for
   everything), and the custom bezier (not a stock ease) is reserved specifically for this
   one signature moment rather than diluted across the whole page.
2. **The ±4px / ±2deg parallax clamp** (`main.js:404-406`). Subtle enough to read as
   "alive," restrained enough to never feel gimmicky or nauseating — the clamp values are
   the actual design decision here, not the mechanism.
3. **The shadow-collapse-on-press pairing.** `drop-shadow(0 20px 17px rgba(222,105,33,.22))`
   idle → `drop-shadow(0 8px 9px rgba(222,105,33,.32))` pressed, synced with `scale(.95)`
   (`style.css:168, 181`) — the shadow tightening and darkening in lockstep with the scale
   sells a physical "pressed into the surface" read that a naive `scale()`-only treatment
   would miss.
4. **rAF-coalesced writes, `will-change` scoped to the tracking window only**
   (`main.js:358-360`, `style.css:177`). Correct, disciplined performance practice —
   exactly one write per frame, and the browser isn't asked to keep a layer promoted when
   the pointer isn't moving.
5. **`.nav-shell`'s glass treatment** (`style.css:71-83`) — `backdrop-filter: blur(17px)`
   with a dual box-shadow (outer drop + inset top highlight) against a semi-transparent
   white fill is the single most refined "material" surface on the page and reads as
   deliberate, not decorative default.
6. **The editorial rhythm of numbered section kickers** ("02 / o que tem no dokke", "03 /
   próximos capítulos", etc., `style.css:312-319`) paired with the tight, heavy display
   type (`letter-spacing: -.075em`, weight 750) gives the page a confident, magazine-like
   structure that most install-pages in this category don't attempt.

### Weak — should be improved in DeckTech, not carried forward as-is
1. **Inter is never loaded.** `font-family: Inter, ...` + `font-synthesis: none`
   (`style.css:11-12`) with no `@font-face`/Google-Fonts link anywhere in `docs/`. Every
   heavy-weight display heading (`font-weight: 750/650/700`) is silently falling back to
   system-font weights on every visitor's browser today, Windows visitors very much
   included. This is the single highest-leverage fix — add a real Inter font source (or
   pick a self-hosted variable font and load it properly) before anything else.
2. **Zero server-rendered content, zero social/SEO meta.** The whole DOM is built by
   `innerHTML` assignment (`main.js:51`) with no SSR/prerender step in the Vite config;
   `index.html` has no `og:*`/`twitter:card`/canonical. For a page whose entire job is to
   get people to click a download link from a shared link, this actively hurts link
   previews and search visibility. Worth a static-prerender or at minimum hand-authored
   OG tags in `index.html`.
3. **The i18n layer has real, user-visible bugs**, not stylistic nitpicks: FAQ-5's bold
   emphasis is destroyed on every load (§6), the version badge never translates (§6), and
   two of three visually-identical pill rows are wired inconsistently (§6). A DeckTech
   rebrand is the natural moment to replace the manual selector-map with something that
   can't silently drop markup or leave orphaned keys.
4. **Mobile nav has no replacement for the hidden links.** `.nav-links { display: none }`
   at ≤760px (`style.css:802`) with no hamburger — Recursos/Comunidade/Docs simply vanish
   below tablet width. This needs a real mobile nav pattern, not a removal.
5. **Reduced-motion's blast radius is too wide.** The blanket `*, *::before, *::after {
   transition-duration: .01ms !important }` (`style.css:790`) kills every hover
   transition site-wide (buttons, nav links, CTA), not just the hero parallax that
   `prefers-reduced-motion` is actually about. Scope the override to the transform/motion
   properties, not all transitions.
6. **Mac-exclusive copy is structural, not cosmetic**, per §7 — `downloads` has no
   `windows` key, the hero/features copy is written "your Mac, on any screen" rather than
   platform-neutral, and `.windows-note`/`faq.6` exist specifically to say Windows isn't
   ready. None of this is a find-and-replace; it's a copy and layout rewrite (third CTA
   button, new hero framing, inverted FAQ answer) that DeckTech's positioning demands.
7. **Design-token duplication between `main.js`'s site and `tutorial-dokke.html`'s
   self-contained deck** (§2) — two independently-maintained palettes for the same brand,
   with the deck also hardcoding its own `theme-color` (`#ff8a38`) rather than referencing
   a shared source of truth. A DeckTech rebrand should either extract shared tokens both
   documents import, or explicitly accept the duplication and keep both in sync by hand
   with a linked checklist.
8. **`dokke-icon.png` at 269KB is an unoptimized outlier** next to the 20KB WebP hero at
   identical dimensions — re-encode when swapping the mark.
9. **Dead code to clean up while rebranding, not carry forward:** the `--purple` token
   (`style.css:8`, never referenced) and the `.download-link`/`.download-link:hover`/
   `.download-link span` rule set (`style.css:112-131, 825-826`, no matching class in
   `main.js` — likely a leftover from before the GitHub button was restyled as
   `.github-link`).
