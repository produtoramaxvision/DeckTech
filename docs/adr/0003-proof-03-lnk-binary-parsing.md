# ADR-0003: Binary `.lnk` parsing in Node vs COM (`WScript.Shell`)

- Status: Accepted
- Date: 2026-09-17
- Requirement: PROOF-03 (`.maxvision/REQUIREMENTS.md` Fase 0), gates PLAT-10
- Supersedes: nothing. First measurement of unvalidated assumption U5
  (`.maxvision/research/SUMMARY.md:646`).

## Context

`.maxvision/research/WINDOWS-STACK.md` measured resolving 149 `.lnk` shortcuts
to their target `.exe` via COM (`WScript.Shell.CreateShortcut(path).TargetPath`)
at 2395 ms total, ~16 ms/shortcut, and flagged reading the `.lnk` binary
format directly in Node as a plausible but explicitly unvalidated
optimization (U5): "Vale ler `.lnk` binário direto em Node (sem COM) para
matar os 16 ms/atalho. Não validei essa otimização."

A binary reader is only worth shipping if it produces the **same** target
list as COM. A parser that is faster and silently wrong on even a few
shortcuts is a regression, not an optimization — a user whose shortcut
resolves to the wrong `.exe`, or to nothing, notices immediately.

## What was built

- `measure/windows/lnk-parser.mjs` — a pure-Node, zero-dependency reader of
  the [MS-SHLLINK] binary format (ShellLinkHeader, LinkFlags, LinkInfo,
  CommonNetworkRelativeLink, StringData, and the EnvironmentVariableDataBlock
  extra-data block), built directly from the Microsoft Open Specifications
  pages (fetched 2026-09-17, protocol revision 10.0, not from memory/recall).
- `measure/windows/lnk-com-resolve.ps1` — the COM baseline resolver, using
  the same `WScript.Shell` mechanism as the original measurement, with one
  COM object reused across the loop and an internal `Stopwatch` around the
  resolution loop only (comparable, per-item, to the 2395 ms/149 baseline).
- `measure/windows/proof-03-lnk-benchmark.mjs` — orchestrates both, does a
  tiered (exact → case-insensitive → `fs.realpathSync.native` filesystem
  identity) item-by-item comparison, and prints/records the result.

## Measured result (this machine, 2026-09-17)

Scope: every `.lnk` under `%ProgramData%\Microsoft\Windows\Start Menu\Programs`
and `%APPDATA%\Microsoft\Windows\Start Menu\Programs` (machine + user),
**182 files** — matching the prior enumeration count in WINDOWS-STACK.md
exactly. The original 2395 ms/149 figure covered a subset of these 182 (the
research doc does not say which 33 were excluded or why); this run
resolves all 182 through both paths rather than reproducing an undocumented
filter.

```
Baseline (research, prior run): 149 shortcuts, 2395 ms total, 16.07 ms/shortcut
COM this run (loop-only, comparable to baseline): 182 shortcuts, 267.9 ms total, 1.47 ms/shortcut
COM this run (wall incl. PowerShell startup + COM instantiation): 615.0 ms total
Node binary parser this run: 182 shortcuts, 33.54 ms total, 0.1843 ms/shortcut
Speedup (COM loop-only / Node parser): 8.0x
```

The COM loop-only number this run (1.47 ms/shortcut) is itself well below
the original 16.07 ms/shortcut baseline — plausibly OS file-cache warmth
from repeated runs during this investigation, or COM overhead variance.
Either way the Node parser is faster than **both** numbers by a wide
margin (8.0x over this run's own COM measurement; ~87x over the original
16.07 ms/shortcut baseline), so the speedup finding is robust to which COM
number is used as the denominator.

Full per-shortcut data: `measure/windows/proof-03-results.json` (182 rows,
regenerated by re-running the benchmark script).

### Agreement

| Tier | Count |
|---|---|
| Exact string match | 170 |
| Case-insensitive match | 0 |
| Same file on disk (`realpath`) match | 0 |
| **Mismatch (different target)** | **0** |
| COM returned empty string | 4 |
| COM returned no result | 0 |
| Parser produced no candidate, COM had one | 8 |

**Zero mismatches.** Every shortcut where COM produced a non-empty
`TargetPath` (178 of 182) was matched at the `exact` tier by the parser —
no case-insensitive or realpath fallback was ever needed on this machine's
shortcut set.

### The 8 shortcuts the parser does not resolve

All 8 are shortcuts whose only path information is a `LinkTargetIDList`
with no `LinkInfo` structure at all (`HasLinkTargetIDList` set,
`HasLinkInfo` not set) — resolving them requires shell namespace lookup
(`SHGetPathFromIDList`/`IShellFolder`), which COM has access to and a pure
binary reader does not, by construction (documented as limitation 1 in
`lnk-parser.mjs`'s module header, not discovered after the fact):

- `HandBrake\Uninstall.lnk` → COM: `C:\Program Files\HandBrake\uninst.exe`
- `MobaXterm\MobaDiff.lnk`, `MobaXterm\MobaTextEditor.lnk` → COM:
  `...\MobaXterm\MobaRTE.exe`
- `Riot Games\League of Legends.lnk`, `Riot Games\Riot Client.lnk` → COM:
  `D:\Riot Games\Riot Client\RiotClientServices.exe`
- `Topaz Video AI\Topaz Video AI.lnk` → COM:
  `C:\Windows\Installer\{CCF2...}\mainapp.exe` (this is also the one
  MSI-advertised shortcut found — see below; it is IDList-only *and*
  Darwin-tagged)
- `Windows Kits\...\Windows Software Development Kit.lnk` → COM:
  `C:\Windows\explorer.exe`
- `Google Cloud SDK\Google Cloud SDK Shell.lnk` → COM:
  `C:\Windows\system32\cmd.exe`

A further 4 IDList-only shortcuts (`File Explorer.lnk`, `Control
Panel.lnk`, `Run.lnk`, `MobaXterm\Visit MobaXterm Website.lnk`) got an
**empty** `TargetPath` from COM too — these are virtual-shell-item
shortcuts with no real filesystem target either way, so there is nothing
for either method to disagree about.

None of these 12 is a mismatch: the parser correctly reports "no
candidate" rather than fabricating a wrong path.

## Category coverage (task requirement: test what exists, report zeros honestly)

| Category | Found on this machine | Parser handles it |
|---|---|---|
| Environment-variable targets (`HasExpString`) | **42** | Yes — extracts `EnvironmentVariableDataBlock`, expands `%VAR%` via `process.env`; in every one of the 42 cases, `linkinfo-local` (when present) or `env-expanded` matched COM exactly |
| UNC path targets (`CommonNetworkRelativeLink`) | **0** | Implemented (`CommonNetworkRelativeLink` parsing, `\\server\share` reconstruction) but **not exercised** — no UNC-targeted shortcut exists in this Start Menu. Not claimed as validated. |
| MSI-advertised shortcuts (`HasDarwinID`/`DarwinDataBlock`) | **1** (Topaz Video AI) | Detected (`category.msiAdvertised: true`) but **not resolved** — by design (documented limitation 2). Resolving it needs the Windows Installer API (`MsiGetShortcutTarget`), not a binary read. This is also one of the 8 IDList-only gaps above. |
| UWP/Store app shortcuts | **0** `.lnk` files exist for these | This is the correct finding, not a parser gap: real Start Menu tiles for UWP/Store apps (Calculator, Photos, Terminal, etc.) are not `.lnk` files at all — they resolve through `shell:AppsFolder`, which is PROOF-02's scope, not PROOF-03's. Scanning the raw bytes of all 182 `.lnk` files (both UTF-16LE and Latin-1 decodings, not just the parsed fields) for `AppsFolder` or the `!App` AUMID suffix found zero matches. |

The env-var category is the one this task named as needing the most care
(raw vs. expanded). All 42 instances resolved via `linkinfo-local` (when
`LinkInfo` was also present and usable) or `env-expanded`; none needed the
raw, unexpanded env-block string to match COM, and none tripped
`ForceNoLinkInfo` (which was checked and honored — see
`lnk-parser.mjs`, "Candidate target paths, in priority order").

## Decision

**Ship the binary reader as the primary mechanism for PLAT-10.** The
measured evidence:

1. Zero target-path mismatches across 182 real shortcuts on this machine,
   at the strictest (exact string) comparison tier.
2. An 8.0x–87x speedup depending on which COM measurement is used as the
   baseline, consistent with U5's hypothesis.
3. A well-defined, honestly-scoped gap (IDList-only shortcuts, ~4–7% of
   this machine's set) with an unambiguous signal when it occurs
   (`resolvedTargetPath: null`, `category.idListOnly: true`) rather than a
   silently wrong answer.

**PLAT-10 must keep a COM (or `IShellLinkW`) fallback for the IDList-only
case**, not replace COM outright. When `lnk-parser.mjs` returns no
candidate, PLAT-02/PLAT-10's app enumerator should fall back to COM
resolution for that one shortcut (an 8/182 ≈ 4.4% fallback rate on this
machine, at COM's ~1.5–16 ms/item cost, is negligible against the ~99.96 ms
saved on the other 174). This ADR does not itself implement that
fallback — it is a decision record for PROOF-03, consumed by PLAT-10
(Fase 3).

**Not validated, flagged for PLAT-10 to re-check if it matters there:**
UNC-targeted shortcuts and MSI-advertised shortcut *resolution* (detection
works; resolution does not and is not attempted). Both are present in the
codebase as documented, deliberate gaps, not silent ones.

## Reproducing this measurement

```
node measure/windows/proof-03-lnk-benchmark.mjs
```

Requires Windows (COM `WScript.Shell` is Windows-only) and PowerShell on
`PATH`. Regenerates `measure/windows/proof-03-results.json`.
